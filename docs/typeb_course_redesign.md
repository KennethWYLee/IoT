# Type B 課程設計：Full-stack IoT 系統設計與實作

本文件依據 `C:\Users\User\Documents\Lecture materials\2026_Oxford EMI\output\TypeB-teaching-redesign-guide.md`，將 IoT 課程設計成「概念判斷、實作驗證、同儕比較、修正與遷移」的循環。完整週次以 `docs/18_week_plan.md` 為主。

## 1. 課程假設

- 對象：資管二年級學生，具基礎程式能力，硬體經驗弱。
- 課程長度：18 週，每週 165 分鐘。
- 分組：建議 3-4 人一組。
- 裝置端：ESP32-S3-DevKitC-1 N16R8 與可選感測器／致動器。
- 手機端：響應式 Web／PWA 為共同要求，Flutter 為進階選項。
- 伺服器端：學生必須自行建立後端、資料庫、結構化 log 與查詢功能。
- 教師的智慧停車場與 UCI 4WD 為整合示範，不是全班共同專題。
- 第 7 週個人概念筆試；第 8 週每組一次概念與技術可行性訪談。
- 第 9 週教師出國，不要求到校、不收新評量成果。
- 第 17 週期末展示；第 18 週只提供進階自學教材。

## 2. Type B 的課堂原則

本課不把一個 20 分鐘的示範拉長成兩小時。示範之後的時間必須用於學生轉換問題、修改規格、整合系統、診斷錯誤與產生可檢查證據。

```text
短講解或示範
  -> 個人預測或判斷
  -> 小組實作與驗證
  -> 比較不同結果
  -> 延後回饋與修正
  -> 套用到自己的題目
```

每個學習循環至少留下其中一種證據：

- 接線圖與安全判斷
- API、topic 或 JSON 契約
- 可執行程式與畫面
- Serial log、server log 或資料庫紀錄
- 錯誤分類與修正前後比較
- 一分鐘口頭說明或 exit ticket

## 3. 課程學習成果

學生完成課程後應能：

1. 區分開發板、感測器、致動器、通訊服務、後端、資料庫與前端的責任。
2. 依電壓、電流與邏輯準位限制，安全完成 ESP32-S3 接線與測試。
3. 設計具裝置、時間、事件與狀態欄位的 JSON 資料契約。
4. 使用 HTTP、MQTT 與 WebSocket 連接裝置、伺服器及手機前台。
5. 建立能儲存、查詢與分析 IoT 資料的後端、資料庫與結構化 log。
6. 透過手機介面觀察即時狀態、查閱歷史資料並下達受控命令。
7. 以故障注入、測試紀錄與可重建部署證明系統的可靠性。
8. 使用 AI 輔助開發後，能人工解釋、測試、修正並承擔設計決策。

## 4. 每堂 165 分鐘建議節奏

節奏可依當週任務調整，不要求每段機械式固定。

| 時間 | 活動 | 學生行動與證據 |
|---:|---|---|
| 0-10 | HOT question | 個人先寫預測、分類或設計判斷 |
| 10-30 | Mini-input 與示範 | 記錄資料流、關鍵限制與預期結果 |
| 30-45 | BIT 1 | 兩人比較答案，說明判斷理由 |
| 45-80 | 引導實作 | 完成共同最小案例並留下第一筆可驗證證據 |
| 80-95 | 錯誤案例與延後回饋 | 先診斷再看教師解釋，修正自己的結果 |
| 95-140 | 遷移任務 | 修改成不同感測器、資料欄位、介面或使用者情境 |
| 140-155 | Share and compare | 比較兩種可行方案及其取捨 |
| 155-165 | Exit ticket | 提交一項成果、一個未解問題與下一步 |

BIT 可使用 Predict、Classify、Transform、Rank、Debug、Complete 或 Test design。活動名稱只是手段，重點是學生必須做出可觀察的判斷與修正。

## 6. 第 7 週個人概念筆試

筆試不是記憶函式名稱，而是檢查學生能否解釋與判斷：

- GPIO、GND、3.3V/5V、共地與安全接線
- sensor、actuator、module、board、backend、database、frontend
- HTTP request/response、MQTT broker/topic、WebSocket push
- JSON 欄位、資料庫紀錄與 structured log 的差異
- 即時狀態、歷史查詢、命令回執與錯誤處理
- 給定資料流或接線圖的除錯與風險判斷

題目可提供程式片段、資料流圖、log 或錯誤畫面，要求學生指出證據與修正方向。

## 7. 第 8 週小組訪談

每組只需到場一次。建議訪談結構：

| 時間 | 內容 |
|---:|---|
| 2 分鐘 | 說明問題、使用者與預期價值 |
| 3 分鐘 | 說明裝置、前後台、資料庫與資料流 |
| 3 分鐘 | 展示一個可運作片段，不要求完整成品 |
| 3 分鐘 | 教師追問技術風險、成本、安全與最小範圍 |
| 2-4 分鐘 | 確認下一步與需刪除的非必要功能 |

訪談評分聚焦：問題是否具體、架構是否合理、風險是否被辨識、工作量是否可完成，以及學生能否解釋自己的選擇。

## 8. 第 10-12 週新內容

### 第 10 週：MQTT 與多裝置

共同情境使用多個虛擬或實體 ESP32。學生需設計 device ID、topic、payload、presence、last will 或等價離線偵測，以及命令回執。重點不是只連上 broker，而是避免訊息送錯裝置並留下證據。

### 第 11 週：資料庫與 log 分析

學生比較 sensor reading、domain event、command 與 system log，決定哪些需要長期保存。實作時間區間查詢、事件次數、錯誤比例、最近狀態或簡單異常摘要，並說明查詢對使用者或維運者的用途。

### 第 12 週：手機前台與雙向控制

共同最低版本使用響應式 Web/PWA，包含即時狀態、歷史資料、事件／錯誤提示與受控命令。Flutter 可以取代 PWA，但不能以只有手機 UI、沒有自建後端與資料庫的作品通過。

## 9. 期末專題最低技術邊界

每組題目可以不同，但必須具備：

1. 至少一種真實感測或實體輸入。
2. ESP32-S3 經 Wi-Fi 傳送結構化資料。
3. 學生自行建立且可重新部署的後端。
4. 資料庫與可操作的歷史查詢。
5. 可搜尋或彙整的 structured log，以及至少一項分析。
6. 手機可使用的前台，顯示即時與歷史資訊。
7. 手機經後端下達至少一種受控命令，裝置回報結果。
8. 一項規則、狀態機、告警或自動化行動。
9. 斷線、錯誤資料或裝置異常的處理與測試證據。
10. 架構圖、資料字典、部署說明、原始碼與 AI 使用紀錄。

## 10. AI 輔助開發的 Type B 證據

學生可以使用 LLM 或 vibe coding，但每一項 AI 產出都要經過人工理解與驗證。可採下列活動：

- 先預測程式會做什麼，再實際執行並比較。
- 找出 AI 生成接線圖、API 或 SQL 的一項風險。
- 對同一需求比較兩個 AI 方案，說明取捨。
- 提交失敗 prompt、錯誤結果、修正方式與測試證據。
- 現場修改一個需求，證明不是只會重播既有 demo。

AI 可以加快輸入，但不能取代學生對接線安全、資料契約、測試結果與系統行為的責任。
