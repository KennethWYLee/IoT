# Type B 課程設計：IoT 玩具與互動硬體

本文件依據 `C:\Users\User\Documents\Lecture materials\2026_Oxford EMI\output\TypeB-teaching-redesign-guide.md`，將 IoT 課程設計成「概念判斷、實作驗證、同儕比較、修正與遷移」的循環。完整週次以 `18_week_plan.md` 為主。

## 1. 課程假設

- 對象：資管二年級學生，具基礎程式能力，硬體經驗弱。
- 課程長度：18 週，每週 165 分鐘。
- 分組：1～3人一組；每組準備一台萬用電表。1人組可與其他組共用電表，
  但各組的量測、判讀與學習證據分開保存。
- 裝置端：ESP32-S3-DevKitC-1 N16R8 與可選感測器／致動器。
- 第2～7週只處理硬體、安全、量測、感測、致動與單機互動；第11週開始連網。
- 手機端：響應式 Web／PWA 為共同要求，Flutter 為進階選項。
- 伺服器端：學生必須自行建立後端、資料庫、結構化 log 與查詢功能。
- 學生可自選玩具或硬體；軟體須記錄資料／事件或協助使用者操作。
- 教師的智慧停車場與 UCI 4WD 為延伸示範，不是全班共同專題。
- 第7、15週各進行一次個人筆試，考試週不安排新進度；第8、12、16至17週
  依序進行三次專題報告。
- 第9週教師出國，不要求到校、不收新評量成果。
- 第17週分批進行第三次專題報告與期末展示；第18週為校定期末考週，
  保留空白，不安排常規教材。

## 2. Type B 的課堂原則

本課不把一個 20 分鐘的示範拉長成兩小時。示範之後的時間必須用於學生轉換問題、修改規格、整合系統、診斷錯誤與產生可檢查證據。

```text
短講解或示範
  -> 個人預測或判斷
  -> 小組實作與驗證
  -> 比較不同結果
  -> 延後回饋與修正
  -> 套用到自己的題目
```

每個學習循環至少留下其中一種證據：

- 接線圖與安全判斷
- API、topic 或 JSON 契約
- 可執行程式與畫面
- Serial log、server log 或資料庫紀錄
- 錯誤分類與修正前後比較
- 一分鐘口頭說明或 exit ticket

## 3. 課程學習成果

學生完成課程後應能：

1. 區分開發板、感測器、致動器、通訊服務、後端、資料庫與前端的責任。
2. 依電壓、電流與邏輯準位限制，安全完成 ESP32-S3 接線與測試。
3. 將輸入、狀態、決策與輸出組成可重複使用並可安全停止的互動硬體。
4. 設計清楚的 JSON 資料格式，使用 HTTP、MQTT 與 WebSocket 連接裝置、伺服器及手機前台。
5. 建立能儲存、查詢與分析 IoT 資料的後端、資料庫與 structured log。
6. 透過手機介面觀察即時狀態、查閱歷史資料並下達受控命令。
7. 以故障注入、測試紀錄與可重建部署證明系統的可靠性。
8. 使用 AI 輔助開發後，能人工解釋、測試、修正並承擔設計決策。

## 4. 不設教材分鐘配額

正式課堂時段不變；教材以入門可理解、清楚與完整為基準，不以固定分鐘表裁切說明。

## 6. 第一次專題報告：第8週題目與技術可行性

每組只需到場一次。建議報告與問答結構：

| 時間 | 內容 |
|---:|---|
| 2 分鐘 | 說明問題、使用者與預期價值 |
| 3 分鐘 | 說明裝置、前後台、資料庫與資料流 |
| 3 分鐘 | 展示一個可運作片段，不要求完整成品 |
| 3 分鐘 | 教師追問技術風險、成本、安全與最小範圍 |
| 2-4 分鐘 | 確認下一步與需刪除的非必要功能 |

第一次報告評分聚焦：問題是否具體、架構是否合理、風險是否被辨識、工作量是否可完成，以及學生能否解釋自己的選擇。

## 7. 第一次個人筆試：第10週硬體接線、電氣概念與安全

筆試不是記憶函式名稱，而是檢查學生能否解釋與判斷：

- GPIO、GND、3.3V/5V、電阻／電壓量測、ADC、共地與安全接線
- sensor、actuator、module與board
- 感測取樣、有效／無效讀值、輸入、輸出與單機狀態機
- 致動器供電、安全停止、timeout與錯誤狀態
- 給定接線圖、量測值或Serial輸出的除錯與風險判斷

題目可提供接線圖、程式片段、量測值或Serial輸出，要求學生指出證據與修正方向。

## 8. 第11～12週及第14週新內容

### 第11週：HTTP、WebSocket、Backend與雙向控制

學生沿用Week 7按鈕與Week 5低功率RGB，依Week 11韌體定義事件並以HTTP送入學生自建Backend，由WebSocket更新手機頁面；不把完整遊戲直接變成遠端致動器。手機送出帶`command_id`的安全命令，裝置回傳accepted、done、rejected、error或timeout。重點是用log分段證明每一層，而不是只看到手機畫面改變。

### 第12週：MQTT訊息與持久化資料

共同情境使用多個虛擬或實體ESP32。學生設計device ID、topic、payload、presence、Last Will或等價離線偵測及命令回執，再讓一項事件與命令結果進入Database。資料庫部分只要求可重建schema、最小歷史查詢與一次跨層log除錯，不擴張成完整資料庫理論課程。

### 第14週：手機前台與雙向控制

共同最低版本使用響應式 Web/PWA，包含即時狀態、歷史資料、事件／錯誤提示與受控命令。Flutter 可以取代 PWA，但不能以只有手機 UI、沒有自建後端與資料庫的作品通過。

## 9. 第二次個人筆試：第16週網路通訊與軟硬整合架構

第二次筆試檢查學生能否追蹤Wi-Fi、HTTP、JSON、WebSocket、MQTT、Backend、
Database、structured log與手機前台之間的責任與資料流。題目可提供signal、
event、command、result、error、timeout、topic、payload、資料流圖或多層log，
要求學生判斷成功證據、中斷位置與安全處理。全週只考試，不安排新進度或實作。

## 10. 期末專題最低要求

每組題目可以不同，但必須具備：

1. 一件可安全操作的玩具或其他實體硬體。
2. 至少一種實體輸入與一種實體輸出；例外須於第8週獲准。
3. ESP32-S3 經 Wi-Fi 傳送結構化資料。
4. 學生自行建立且可重新部署的後端。
5. 資料庫與可操作的歷史查詢。
6. 可搜尋或彙整的 structured log，以及至少一項分析。
7. 手機可使用的前台，顯示即時與歷史資訊。
8. 手機經後端下達至少一種受控命令或設定；裝置回報結果。
9. 一項規則、狀態機、告警或自動反應。
10. 斷線、錯誤資料或裝置異常的處理與測試證據。
11. 架構圖、資料字典、部署說明、原始碼與 AI 使用紀錄。

## 11. AI 輔助開發的 Type B 證據

學生可以使用 LLM 或 vibe coding，但每一項 AI 產出都要經過人工理解與驗證。可採下列活動：

- 先預測程式會做什麼，再實際執行並比較。
- 找出 AI 生成接線圖、API 或 SQL 的一項風險。
- 對同一需求比較兩個 AI 方案，說明取捨。
- 提交失敗 prompt、錯誤結果、修正方式與測試證據。
- 現場修改一個需求，證明不是只會重播既有 demo。

AI 可以加快輸入，但不能取代學生對接線安全、資料契約、測試結果與系統行為的責任。
