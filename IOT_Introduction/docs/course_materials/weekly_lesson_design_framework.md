更新日期：2026-09-06。

本文件供教材維護者用來產生、修訂與驗收每週教材。以目前
[Week 2主教材](../../Week_02_ESP32_Hardware_Basics/week2_main.ipynb)與
[Week 3主教材](../../Week_03_Electrical_Measurement_and_ADC/week3_main.ipynb)
的初學者問答、操作修訂及[聯合檢查紀錄](../lab_notes/2026-09-05-week2-week3-beginner-review.md)
為設計參照，不把它們當成所有內容均已實機驗證或所有學生均已試讀通過的樣板。

目標是產生好懂、清楚、完整、適合入門者的文件。第一次接觸硬體的學生不只要知道
「下一步按哪裡」，還要能說明「為什麼這樣做、正在觀察什麼、結果能證明什麼、
結果不同時如何安全檢查」。依教師最新決定，教材不受150分鐘或其他授課時間、
篇幅與頁數限制；需要的基礎解釋、範例、推導、圖解與排錯都要保留並補齊。

詳細程度以能否理解為準。內容可以很長，但必須有清楚的先備順序、章節與交叉引用，
不能用重複堆砌代替解釋，也不能為了簡短省略學生還不會的關鍵推理。

## 二、核心教學循環與先備順序

> 辨認 → 理解 → 預測 → 操作 → 觀察 → 解釋 → 排錯 → 深入練習 → 保存證據 → 安全復原

這是學習關係，不是要求每節套用相同標題或重複十次同一張表。

- **辨認**：先在實物、絲印、軟體畫面或資料中找出本步驟使用的對象。
- **理解**：名詞第一次影響操作時，說明它是什麼、此處有何作用、現在如何使用。
- **預測**：在揭示結果前，讓學生先說明可能看到的方向、狀態或數量及理由。
- **操作與觀察**：提供可重現步驟、正常現象及需要保存的原始資料。
- **解釋**：每完成一個關鍵操作就說明原因與證據界線，不累積到最後才補全部理論。
- **排錯與深入練習**：先安全檢查，再一次改一個條件，比較、修正並說明限制。
- **保存與復原**：明確指定紀錄方式、保留版本與安全結束狀態。

概念安排遵守「具體對象 → 問題 → 名稱與單位 → 完整例子 → 公式或程式 →
結果判讀 → 相近反例」。不能先要求學生辨認模組三個腳位，數節後才提供實拍；
不能在學生還不懂V、Ω、A時先要求計算上拉支路電流。

比喻須回到實物與操作。例如用「尺的兩個端點」解釋電壓差後，要指出實際兩個測點，
不能讓學生把比喻中的距離直接當成GPIO的HIGH判定。必要時寫明比喻不適用之處。

### 說明深度的檢查問題

每個核心概念依其用途檢查學生是否能回答：

1. 它是什麼，和容易混淆的另一個名稱差在哪裡？
2. 它在哪裡，在照片、程式、電路或畫面上怎麼找到？
3. 這一步為什麼要用它，不做或做錯會有什麼差別？
4. 操作前、操作中、操作後，電路或資料發生什麼改變？
5. 預期現象為什麼出現，哪些細節影響結果？
6. 數字或狀態是如何取得的，實際代表什麼，又不能證明什麼？
7. 換一個數值、方向或情境時，能否使用同一個原理解釋？
8. 結果不同時，如何先確保安全，再判斷是操作、設定、模型限制或未知原因？

這些是編輯檢查，不必逐題貼到每一節。不要假設「學生具程式能力」就已懂電氣、
單位、儀表或電路圖；若回答要用到尚未教過的概念，先補必要說明。

## 三、Teaching Point對照與對齊

Teaching Point是一項真正要教、操作或判讀的能力。修改前建立內部對照，每列記錄：

| 欄位 | 必須能回答的問題 |
|---|---|
| ID與正式範圍 | 教哪一項能力？哪些相近內容不教？ |
| 先備能力與版本 | 學生之前在哪裡學過？目前硬體、程式或系統應在什麼狀態？ |
| 可觀察成果 | 學生能辨認、量測、執行、解釋、比較或修正什麼？ |
| 來源與證據類型 | 官方位置、程式、照片、實測或教學模型是哪一份？有哪些限制？ |
| 講解位置 | 首次必要解釋放在哪一節？是否早於第一次使用？ |
| Worked example | 從開始狀態、已知條件到結果判讀的完整例子在哪裡？ |
| 圖解與對照 | 此處需要照片、接線圖、原理圖、流程圖、時間軸或表格嗎？要解決哪個誤解？ |
| 學生練習 | 學生要預測、改變、比較、量測、判讀或除錯什麼？ |
| 預期結果與回饋 | 正常現象、反例、結果不同時第一個安全檢查是什麼？ |
| 完成與證據 | 怎麼保存？什麼足以支持結論，什麼仍不能證明？ |
| 評量連結 | 對應哪一項課堂成果、已核准考試或報告能力？ |
| 驗證狀態 | 文件、計算、compile、host、simulation、target、physical及試讀哪些已做？ |

對照表是維護工具，保存在既有審查位置或工作回報；不在週次資料夾新增第三份文件。
每個正式內容都要有講解、完整示範、學生練習、預期結果及回饋。多項緊密相關內容可共用
一個逐步例子，但各自的解釋不能消失。Type B討論不能取代講解與完整示範。

考試能力須在考前教過、示範並練習；報告要求須有前置教學與實作時間。不因補充頁
出現新名詞就增加必考或必做內容，也不把同一成果另立新項目重複計分。

取樣（sampling）與門檻（threshold）。後續可以中文簡稱承接，不反覆堆疊雙語。
實體型號、腳位標示、程式識別字與軟體選單不翻寫，例如寫成接地腳位（GND）、
內部上拉輸入模式（`INPUT_PULLUP`），程式中的`INPUT_PULLUP`仍維持原樣。

內容依理解順序分層，但不拆成多個學生入口，也不以授課時間決定刪除哪些說明：

  若某段推導是理解當前例子的必要條件，就留在當前位置，不能為縮短正文藏到附錄。

- 引用必讀前節要有明確標題或連結；不能把完成操作所需資訊藏在模糊的「詳見附錄」。
- 長文件用語意清楚的章節、必要的章內導覽與階段小結協助定位。每個小結說明已理解
  什麼、目前線路／程式狀態及接下來的問題；不另建一份省略細節的主要教材。

## 五、數字、單位、公式與推論的教法

### 5.1 先說明數字回答哪個問題

首次使用一個數值時，交代對象、取得方式、單位／尺度、參考點與適用條件。
沒有單位的狀態碼或識別碼，也要說明它不是大小量測。

以Week 2／3的問答為基準，不能只說「0.6很小」「21%不多」「有聲音就是正常」。
要讓學生知道是在什麼功能、什麼測點或什麼分母下，這個數字才有意義。

### 5.2 完整計算範例

需要公式的正式內容，至少有一個以下步驟完整呈現的例子：

1. 用具體情境提出問題，先列已知、未知與測點或資料來源。
2. 解釋每個符號、單位與對應元件／資料，先統一單位。
3. 說明為什麼能用這個關係，再帶入數字，不跳過關鍵步驟。
4. 把結果翻回一句操作上有意義的話，區分量到、算出、命令與推測。
5. 用回算、單位或已知邊界檢查；指出模型假設及不能推廣的情況。
6. 只改一個條件讓學生先預測，再計算或觀察；附上回饋依據。

一個例子是最低要求，不是寫完就停止。若學生仍無法轉用，應補同一原理的對比例子：
先固定其他條件只改一個數值，再比較正確推理與常見錯誤。每個新增例子須說明它解決
哪個不同的理解缺口，不只換數字重印整段答案。

例如，在理想直流電阻模型中，同一顆1 kΩ電阻兩端為3.0 V：

- 已知：這顆電阻兩端的電壓差3.0 V，阻值1 kΩ＝1000 Ω；未知是流過它的電流。
- 依I＝V÷R：3.0÷1000＝0.003 A＝3 mA。
- 回算：0.003 A×1000 Ω＝3.0 V。
- 3.0 V與3 mA不是同一種量；這裡的3 mA是計算值，不是電表V檔直接量出的值。
- 不能任選電路中另一對測點的電壓，除以不對應的電阻；分壓要先標清元件與測點。

關係依[Fluke歐姆定律說明](https://www.fluke.com/en-us/learn/blog/electrical/what-is-ohms-law)；
上述數值配置是教學模型，不是指定板卡的實測結果，也不授權新增電流檔實驗。
後續分壓、取樣間隔、去抖等待、記憶體比例及資料分析沿用同樣的推理順序，
不必每週重教歐姆定律。

### 5.3 電表讀值必須包含完整脈絡

電表範例與紀錄要把以下五欄寫清楚，並交代是否供電及儀表型號：

| 欄位 | 要保存或解釋的內容 |
|---|---|
| 功能與量程 | Ω、直流V或通斷等符號，以及實際量程；不只說顏色 |
| 兩個測點 | 紅、黑表筆各碰哪個元件端點、腳位或延長端 |
| 完整顯示 | 正負號、小數點、數字位置、單位與狀態提示；不是只抄一個整數 |
| 換算或狀態 | 例如V、Ω、kΩ，或「開路／超量程尚未分清」；不能硬填推測值 |
| 判讀與限制 | 支持什麼結論、還有哪些可能原因、第一個安全檢查是什麼 |

範例須區分「功能」「量程」「讀值」；相同的0.6搭配Ω、kΩ或V，不是同一個量。
依該儀表說明辨別最左側單獨1、一般數值1.00與OL等狀態；不可把某型號規則推廣到
所有儀表。蜂鳴是該儀表依其條件給出的提示，不是精確阻值，也不等於整個電路安全。

直流電壓圖應把紅表筆測點減黑表筆測點寫在圖旁，用正反接例子解釋正負號；
V、I、R不能互相加總。硬體上的同節點、電壓差與GPIO數位判定也須分開：
某點的電壓值不是不分規格都能直接叫作HIGH或LOW。

缺少確切儀表手冊、精度、接觸狀態或完整畫面時，保留未確認。歷史回報的
「30–80」「5x」不得擅加Ω或補造小數點，也不能只依數字確診接觸不良。

## 六、步驟、接線與跨階段狀態

每個關鍵步驟必須回答開始狀態、操作對象、確切動作、正常現象、現象意義、
第一個安全檢查、完成條件與證據。「接好線」「確認正常」不足以構成步驟。

### 6.1 用同一套名稱連起實物、圖與程式

- 先固定照片方向與可辨識參照物，避免只有「左上」「右下」而沒有朝向。
- 區分PCB絲印、元件名稱、GPIO編號、程式變數與麵包板孔位，不把row 6當GPIO6。
- 接線表寫完整起點、終點與公／母接頭；線色只能輔助辨認，不能成為電氣功能定義。
- 原理圖說明為何接；接線圖說明如何接。必要時用節點對照把兩張圖與表格連起來。
- 先解釋verified profile是已核准的腳位用途表，再要求使用。照片、編譯或候選測試
  不等於已發布profile；保留PROJECT要求的placeholder與安全閘門。
- 不把原廠DevKitC-1、相容板卡或相似模組的接頭位置直接互換；以確切版型為準。

### 6.2 每次換實驗要交代上一個狀態如何結束

在需要轉換之處，用短表或清楚步驟說明：

1. 前一階段留下哪些電源、接線、程式與服務。
2. 哪些要先停止或斷電，哪些線要拆除，哪些應保留。
3. 新增或移動哪些線、測點、程式、資料或設定；必要延長端在供電前準備。
4. 如何確認不再執行舊程式，或不再把前一階段輸出接到新的感測訊號。
5. 下一階段的第一次安全檢查與正常起始現象。

Week 2至Week 3的舊按鈕／舊孔位、GPIO輸出轉S電壓、S電壓轉ADC，都是這類銜接。
未來網路週同樣要交代舊服務、Port、Database與前台版本，不能只寫「沿用上週」。

### 6.3 依單人可操作性檢查步驟

學生即使分組，也可能一人持表筆、按按鈕並閱讀畫面。不能寫出需要第三隻手、
帶電插拔、硬把粗表筆壓進麵包板或同時握多個裸露導體的必做步驟。

需要延長端或固定方式時，明確交代材料、準備時機、兩端接法、表筆接觸位置、
裸露端隔離與用完如何拆除。未實際試做只能標示為待驗的操作方案，不能宣稱方便。
不得未經核准增加共同採購。重複的安裝／接線只保留一次，後面核對狀態而非要求重做。

## 七、圖解與實拍的設計標準

圖片依要解決的理解問題選擇，不要求固定張數：

| 理解問題 | 合適的圖或對照 |
|---|---|
| 不知道哪一個零件、插孔、絲印或選單 | 確切實拍／介面截圖，標示方向與目標 |
| 不知道線應插哪裡 | 清楚接線圖與起點／終點表，保留孔位和腳位名稱 |
| 知道接法但不懂為什麼 | 原理圖、節點對照、閉合路徑或並聯支路圖 |
| 混淆數字、單位、量程或百分比 | 顯示畫面對照、單位換算表或容量分母圖 |
| 不理解先後、延遲或狀態改變 | 流程圖、時間軸、狀態轉換與對應log |
| 不理解資料如何跨元件流動 | 帶欄位名稱、來源、目的地及回應方向的資料流圖 |

每張圖都須符合：

1. 在第一次需要辨認／操作時出現，圖前先說明要看什麼；不能先給錯誤接法照片，
   圖後數段才補「不要這樣接」。
2. 標明是實拍、理想模型、模擬LCD／log、比較圖或禁止接法。未壓入、未接完、OFF狀態
   等不等於當前目標狀態的照片，須在圖前說清楚。
3. 只畫本圖要解釋的必要關係，首次說明線、箭頭、接點、交叉、顏色與元件符號的意義。
   電流路徑、訊號方向與資料流不能使用同一種箭頭卻不解釋。
4. 相同節點、名稱、正負號、單位、數字與程式／接線表一致；電表支路不畫成所有負載
   電流都必須經過電壓表。用圖旁文字走完至少一條與當前問題相關的路徑。
5. 實拍不能靠生成式補繪猜測腳位、晶片、端子或儀表讀值。保留原圖來源；標註或裁切
   版本須可追溯，不能取代技術驗證。
6. 每圖有有意義的替代文字。圖中文字、箭頭、表格與單位在實際閱讀尺寸下可辨識，
   不以「能載入」取代人工檢閱；必要時拆開過密圖，不靠縮字塞滿。
7. notebook內圖片應在預期平台可顯示。延續Week 2／3的PNG／JPEG附件方法；
   SVG保留為可維護來源，不假設每個平台會渲染SVG或Mermaid。
8. 修改產生圖的build來源，再重建SVG／PNG／notebook附件；若使用原始照片，不因
   搬動章節而遺失附件或重複嵌入無人引用的資料。照片與示意圖分別查核。
9. 桌面與窄螢幕預覽都檢查，讀取PNG、檢查文字和箭頭；本機HTML通過不等於GitHub
   notebook已通過，遠端未檢查須明說。

## 八、程式與輸出的完整教學

- 先說明程式目的、開始狀態與實體／資料關係，再提供完整版本與執行順序。
- 第一次出現的常數、函式、狀態、時間單位與欄位就地解釋。用「名稱指向哪個GPIO、
  何時改變狀態、為什麼要等待」說明，不只逐字翻譯語法。
- 區分電腦執行與ESP32執行的程式；Arduino code cell是供複製編譯的內容時要明說，
  不能讓學生以為在Python notebook按Run就會上傳。
- 寫出必要選單、檔案、環境、依賴、設定及版本。COM編號以目前電腦辨識為準，
  歷史COM8等只是紀錄，不是所有學生固定答案。
- `Sketch uses...`及`Global variables use...`要解釋各自的分子、分母與限制，
  不把程式分割區當整顆Flash，也不把靜態RAM比例當執行期全部RAM或PSRAM占用。
- 時間值說明單位、起點及何時歸零；範例log逐欄對照操作，不只要求學生截圖。
- 分開判定Verify／compile、Upload、Serial、host、simulation與實體反應。
  `output=HIGH`或`done`等文字的證據能力，取決於程式實際回報哪一層。
- 記錄命令、接受、完成、錯誤與timeout，未來網路教材須解釋其資料來源，不把
  手機顯示已送出當成致動器已動作。
- 保存原始log要給出檔名、儲存位置、擷取範圍與核對方法；區分輸出區與輸入／傳送區。
  缺字、截斷或漏失不能用理論值補齊。
- notebook程式副本與`IOT_Introduction/examples/`的維護來源同步；沒有執行的cell保留未執行狀態，
  教學模擬結果不要填成假的執行輸出。保留安全預設、timeout與輸入檢查。

## 九、單一主題Discussion與解答品質

一般教學週只選一個統整當週內容的主題，依「概念與原因 → 原始觀察 → 事前預測 →
控制變因 → 比較／修正 → 證據結論」加深。多題可以共同探討同一主題，不拼湊互不相關
的收尾清單；不以抄寫log或重做已完成步驟代替理解。

- Week 2基準：先解釋官方contact bounce／debounce機制，再比較raw與stable事件、
  等待時間、短按與延遲。課程改寫名稱、時間門檻及接線須與官方原例分開。
- Week 3基準：先問「數字變大，就代表光比較亮嗎？」再連結電阻、分壓、S電壓與raw，
  用同一主題的固定電阻交換練習檢查推理。正式光線條件、筆數與任務依PROJECT。
- 每項練習都要有開始狀態、學生要改什麼、保持什麼不變、可觀察結果與回饋方法。
- 有足夠既有紀錄可回答問題時，先分析紀錄；不為格式要求全部重做。確需補測時，
  具體說明缺少哪個證據，以及補測如何影響結論。
- 未觀察到彈跳、資料範圍重疊或未得到理想值，也可能是合理結果。不能要求學生
  製造符合答案的log、挑選好看的數據，或進行危險故障注入。
- 可用標示清楚的紙上／模擬反例討論未必能安全重現的錯誤；不可冒充實測。

有答案授權的版本，參考解答至少包括：推理步驟、必要圖／計算／log對照、結果的意義、
常見錯誤、不同實測結果的合理解釋與結論限制。題目先出現，解答在後並以題號對應。
設計題可有多種有證據支持的答案；理想計算值不能變成未經驗證的實測容許誤差。

## 十、把學生提問整理回教材

學生問「不懂」「為什麼」「哪一個」就是教材缺口的線索，不把聊天原文整段貼進main。
處理順序為：

1. 在維護紀錄保留必要原問、當時步驟、板卡／程式／檔位與原始回報；不補造情境。
2. 找出真正缺口：名詞、量綱、方向、對象、先備、狀態轉換、實際操作困難或證據不足。
3. 將回答改寫成適合所有初學者的正式說明，使用具體例子；必要時配圖、反例或短表。
4. 放到第一次會卡住的位置，而不是全部堆到最後的Q&A。重複問題合併，正文與答案可
   短提醒連回完整解釋。
5. 修正正文後，同步核對圖、接線、程式、預期結果、練習與完成條件。
6. 用原問題再讀一次：學生能否指出實物、說出數字意義、解釋原因及下一個安全動作？
   若仍只能靠教師口頭提示，持續修訂並記錄尚未解決之處。

例如「3V3不是接a6嗎？」表示抽象電路省略了實際孔位與延長端；「0.6代表什麼？」
表示缺少功能、量程與單位；「為何不是看S？」表示供電回路與量測訊號的關係未說清楚。
修正的是這些理解關係，不要求每週照抄Week 2／3問答或相同硬體案例。

## 十一、以入門理解與完整度決定內容，不設時間上限

不以150分鐘、某次課堂能否教完或固定頁數限制教材。也不要求維護者用分鐘配額決定
哪些內容必須省略。只要是理解、操作、判讀或安全所需，即使增加篇幅，也須完整說明。

撰寫與驗收依下列優先順序：

1. 正確與安全：不以易懂為由省略成立條件、風險或未知之處。
2. 入門可懂：從實物與具體問題開始，先解釋名詞、方向、單位，再推理。
3. 完整可重現：保留必要準備、完整程式、每個操作理由、結果與排錯。
4. 詳細且有層次：需要多少例子、圖、推導就補多少；用章節、對照與小結保持好讀。
5. 可驗證：資料與模型分開，能檢查學生是否理解，而非只做出現象。

取消教材時間限制不等於改變正式週次、上課時段、報告時間或評量，也不代表可以
任意加入不相關的新技術、硬體或必做任務。必要基礎說明可充分展開；若要改課程
範圍、把進度跨週搬移或增加採購，仍須依PROJECT取得教師決定。

一般教學週依正式進度整理成完整單元；Week 1是課程介紹，不硬套硬體實作流程。
考試週只處理規則、範圍與準備；報告週只處理要求、證據與流程，不加入新單元。
教師出國週不新增必做成果；Week 18保留檔案空白。特殊週不為套用模板新增Discussion。

## 十二、逐週產生、修訂與反覆驗證

只在使用者指定範圍內依正式教學順序處理，一次完成一週，再進入下一週。若只要求
某一週，就在該週交付；若要求多週，完成下列紀錄後可自動繼續，不等待重複指示。

1. 完成第一節閱讀，列出本週正式／不教內容、讀者版本、既有狀態與直接依賴。
2. 建立Teaching Point對照及先備順序，找出缺少講解、範例、練習、回饋或圖解的位置。
3. 修正真正維護來源，保留已正確內容；先補必要理解，再刪重複與不相關口吻。
4. 逐句檢查標題、段落、表格、圖說、公式、程式註解、輸出、題目及答案：
   正確性、來源、術語、主詞、方向、單位、成立條件、初學者可懂性與前後一致。
5. 從初學者視角順讀一遍；只使用此前已提供的資訊，檢查每次操作是否有足夠前置資訊。
   遇到要猜方向、孔位、檔位、檔名或舊狀態的地方，視為未完成。
6. 依第十三節執行適用的文件、生成、計算、程式、視覺與硬體檢查；實際閱讀輸出。
7. 發現問題後修正、重新生成並重跑受影響檢查；不是只修文字或只讓測試通過。
8. 建立本週交付紀錄，列出檔案、範圍、主要缺口與修正、實際測試及版本、
   未驗證項目、已知限制與是否可繼續下一週。
9. 多週完成後檢查學習銜接、名稱、欄位、接線profile、評量前置與正式進度一致；
   不宣稱未處理週次也已完成。

硬體不在場可完成文件、compile與host可驗證範圍並繼續下一個已授權單元，但不得
越過尚未核准的安全條件帶學生操作，也不得發布未驗證腳位或宣稱實機完成。
若現有安全證據不足以確定接法，先保留安全閘門並指出待驗，不以猜測填滿教材。

## 十三、分層驗證與圖文驗收

檢查方式與依賴以[scripts說明](../../scripts/README.md)為準。下列是目前存在的命令
示例，從repository根目錄依任務選用，不代表後續每週已有同名腳本：

```powershell
python IOT_Introduction/scripts/verify_course_materials.py
node IOT_Introduction/scripts/build_week2_figures.cjs --check
node IOT_Introduction/scripts/verify_week2_notebook.cjs --render
node IOT_Introduction/scripts/verify_week2_notebook.cjs --compile
node IOT_Introduction/scripts/build_week3_figures.cjs --check

node IOT_Introduction/scripts/verify_week3_notebook.cjs --render

node IOT_Introduction/scripts/verify_week4_notebook.cjs --render

git diff --check
```

Week 5的共用命令可將5替換成6或7，逐週處理，不另編造工具名稱。

只有改圖時才先執行對應build重建，再用`--check`核對；Week 3編譯依既有Arduino檢查
方式處理，不發明不存在的`--compile`功能。其他週以其實際存在的編譯或tests為準。
只有框架Markdown改動而未改教材、圖、程式時，執行文件與差異檢查即可，不為表格
好看重新宣稱編譯或實機通過。

各層分開記錄：

- **文件**：目錄形式、標題語言、內部連結與錨點、表格、code fence、附件引用與重複。
- **來源與計算**：核心技術主張、已知／未知、單位、測點、分母、模型假設與回算。
- **生成一致性**：圖的維護來源、SVG／PNG、notebook附件及程式副本一致。
- **視覺**：實際render並人工讀圖；檢查桌面／窄螢幕、文字、箭頭、單位、圖說與順序。
- **語法／編譯**：記錄CLI、board package、FQBN與library版本，閱讀摘要及警告；
  通過不表示已Upload或實體動作正確。
- **Host／simulation**：記錄輸入、預期、實際輸出、邊界與模型範圍。JS模型通過不是
  Arduino韌體已執行，也不能證明某顆按鈕一定有相同彈跳。
- **Target／physical**：只記錄確實在指定板卡、接法、供電及程式版本下做過的項目；
  使用者提供的歷史log不能代替未完成的現在測試。
- **初學者試讀／試做**：記錄從哪一狀態開始、卡在哪一句、需不需要額外提示、
  是否能解釋數字與圖。耗時若有紀錄只用於了解學習情況，不作教材長度的淘汰門檻；
  單次試做不能推廣成所有學生的保證。
- **發布**：另查讀者版本、答案授權、秘密／個資與預期平台顯示；本機render不能
  代替GitHub驗證，未發布也不能說已同步GitHub。

測試缺環境時，先查既有依賴與可用方法；仍無法執行就記錄原因，不填「通過」。
測試斷言只涵蓋明列項目，圖片數量、檔案存在、exit code 0都不能取代內容審閱。

## 十四、完成判定與交付

可將單元標示為「目前環境可驗證範圍內完成」的條件：

- 正式Teaching Points均有來源、先備順序、講解、完整例子、練習及回饋。
- 首次必要說明與圖解早於操作；每個數值、公式、狀態及結論有足夠脈絡。
- 跨階段有清楚開始／結束狀態，沒有重複或相互矛盾的接線、程式與圖。
- Discussion只聚焦當週核心主題；答案版本符合核准範圍，證據與模型清楚分開。
- 必要定義、例子、推導、圖解、操作理由與排錯已完整展開，不因時間或篇幅刪減；
  長文件仍可依章節定位，選讀與必要內容可辨識，未改變核准範圍。
- 所有可合理執行的適用檢查已做，輸出已讀，已知阻擋性問題已修正。
- 未完成的實機、GPIO核准、初學者試讀及平台驗證明確列出，不寫成已通過。
- 已依AGENTS檢查資料、版本與Git差異，保留使用者既有工作。

交付要同時回答「改了什麼」與「對初學者還有哪些限制」，並列出實際檢查與下一個
必要驗證。可以說「已補齊本次找到的理解與操作缺口」，不能僅憑compile與render
說「零基礎學生一定能獨立完成」。不以某個課堂時限作為完成判定。

本框架定義的是可持續修訂的方法，不是永遠完美的保證；後續實際提問仍依第十節整理
回教材。完成目前授權範圍後交付，只有使用者另有要求才commit、push或擴大處理範圍。
