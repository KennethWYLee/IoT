# 評分規準與檢核表

## 1. 全學期評量

| 項目 | 比例 | 主要證據 |
|---|---:|---|
| 平常成績 | 待教師確認 | 每週實作、QA、文件、安全、協作與 AI 使用驗證 |
| 第一次專題報告（第10週） | 15% | 題目、硬體片段、軟體用途、架構、材料、風險與驗收條件 |
| 第一次實作考（第8週） | 待教師確認 | 以已教、已練的材料與操作完成指定功能；正式規則另訂 |
| 第二次專題報告（第13週） | 15% | 目前實作證據、進度狀態、問題與風險分析、回饋及修正計畫 |
| 第三次專題報告（第17週） | 25% | 完整實體互動、前後台、資料、可靠性、測試、文件與個人理解；每組依排定場次報告一次 |

## 3. 第一次專題報告評分表（第10週，15分）

| 面向 | 分數 | 達標證據 |
|---|---:|---|
| 實體作品與使用情境 | 3 | 說清楚誰操作、作品做什麼、成功如何判斷 |
| 硬體片段 | 3 | 至少一項真實輸入或輸出可運作，並能說明供電與安全 |
| 軟體用途與資料流 | 3 | 明確說明要記錄什麼或如何協助操作，並畫到 Backend／Database／Phone |
| 技術可行性 | 3 | 材料、成本、供電、驅動、網路及工作量合理 |
| 風險與下一步 | 3 | 提出三項具體風險、Week 13進度里程碑與期末最低可驗收結果 |

第一次報告不是完整成品評量。若題目過大，教師應以刪減功能的書面回饋協助縮小，
不得用「還沒做完」重複扣分。

## 4. 第一次實作考準備（第8週）

只評量已教、已練過的材料與操作。正式命題前，由教師確認時間、個人或分組、可用資料與程式、AI 規則、配分、設備故障處理及合理調整，再另建版本化試卷、參考做法與可觀察評分標準。

本次重建不提前公開正式題目或把課堂 Main 當成正式試卷，不沿用已取消筆試的比例與藍圖。

## 5. 第16週一般實作課

依回饋修正期末作品的接線、程式及整合，確認修正後的實際結果。不另辦第二次考試，也不自行新增繳交包或配分。

## 7. 第三次專題報告評分表（第17週，25分）

所有組別在第17週展示，每組一次並保留每位組員的個人問答。所有組別須在第17週第一次展示前依相同截止時間
提交展示commit或tag、文件與測試證據。截止後只允許修復啟動、網路或設備
故障，不得增加評分功能。

| 面向 | 分數 | 高分證據 |
|---|---:|---|

### 評分邊界

- 不因購買昂貴模組、機構華麗或速度較快直接加分。
- 基礎元件只要形成可靠互動、完整資料與清楚使用流程，可取得滿分。
- 只有硬體、沒有軟體紀錄／操作，或只有網頁、沒有真實硬體，均不符合最低要求。
- 現成 dashboard 可以輔助，但不能取代學生後端、Database 與手機介面。
- 純監測題目若已在第10週第一次報告核准無致動器例外，依其告警／分析與使用價值評分。

## 10. 教師巡迴追問

### 硬體

- 這條線是 power、GND 還是 signal？電壓與方向是什麼？
- 誰供電給致動器？ESP32 與外部電源在哪裡共地？
- 開發板重開機或網路斷線時，實體輸出停在哪個狀態？
- 拔掉感測器後，作品怎麼判斷資料不可信？

### 軟體與資料

- 哪一筆資料證明硬體真的執行，而不只是手機按鈕被點擊？
- Event、command、result 與 system error 分別存在哪裡？
- WebSocket 斷線時，手機如何避免顯示過期狀態？
- 請從一筆 log 追到 ESP32 行為與 Database 紀錄。

### 測試與 AI

- 三次測試的差異是隨機、硬體、程式還是操作造成？
- AI 建議中哪一部分曾經不正確或不安全？你怎麼發現？
- 換一台電腦如何啟動？哪些秘密不能放進 repository？
- 哪個限制仍未解決，因此你們沒有宣稱什麼？
