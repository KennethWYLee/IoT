## 做一個看得到、停得下來的倒數器
> 先逐個模組做成功，再把它們接成同一個作品。

上週我們讓感測器回報資料。這週改練輸出：讓燈號與小螢幕告訴使用者，作品現在正在做什麼。

{{diagram:overview}}

完成後，送出 s 會開始 30 秒倒數，紅綠燈每 3 秒輪換；送 x 可以中止。時間到，燈關閉，畫面顯示到期。

本週**不計遮光得分、不接舵機或電池**。螢幕上的 DEMO 數字由我們輸入，不是感測器計分。

我們照講義一起做，先看到結果，再解釋原理。整段程式放在後面，操作時先改設定，不必先讀完所有程式。

## 先把自己這組的腳位寫清楚
> GPIO 編號看板上標示，不是從第一根排針開始數。

下表是教師 BOARD-T01 曾有功能反應的接法，**不是整批器材的安全認證**。只有課前核對後確認適用，才依它填設定；不同板子要使用自己的已確認表。

| 功能 | T01 既有紀錄 | 本組確認值 |
|---|---|---|
| RGB 紅／綠／藍 | GPIO15／16／17 | ＿＿／＿＿／＿＿ |
| RGB 共同端、亮燈準位 | − 接 GND；HIGH 亮 | ＿＿／＿＿ |
| OLED 資料／時脈 | GPIO8／9 | ＿＿／＿＿ |
| OLED 電源、位址 | 3V3／GND；0x3C 有回應 | ＿＿／＿＿ |
| OLED 驅動選項 | 1315 有基本顯示回報 | ＿＿ |

> R 是紅，G 是綠，B 是藍。

## 先讓電腦準備好
> 模組都先不接 ESP32，板子只接 USB。

1. 在 Arduino IDE 用「檔案 → 開啟」打開 [RGB／OLED 倒數程式](../../../examples/week05_rgb_oled_timer/week05_rgb_oled_timer.ino)。`.ino` 放在同名資料夾；IDE 詢問時同意建立。
2. 開啟左側**程式庫管理員**，搜尋 **U8g2**，作者 **Oliver Kraus**，安裝教材對照的 **2.36.15**。已裝相同版本不重裝。
3. RGB 測試雖還不用螢幕，這支完整程式仍需 U8g2 才能編譯。`Wire` 隨 ESP32 套件提供，不另找同名程式庫。
4. YD／CH343 板的 USB 線接背面標 **COM** 的接頭。依這片板的既有設定選 **ESP32S3 Dev Module**、實際連接埠，UART 路徑使用 **USB CDC On Boot: Disabled**。
5. 用左上**勾號 Verify** 檢查編譯。右箭頭 **Upload** 才是上傳。

程式原始值 `LESSON_STAGE=0` 會阻擋輸出，下一頁才改成第一輪。這不是程式壞掉。

<aside>COM 接頭是板上的插孔；COM8 等名稱是電腦的埠號。每台電腦可能不同，不照抄教師號碼。</aside>

## 先選 1，只填 RGB 設定

| 在程式開頭搜尋 | 填入內容 |
|---|---|
| `LESSON_STAGE` | 1 |
| `DEVICE_ID` | 例如 `"group01"`，保留雙引號、不填姓名 |
| `PIN_RGB_R`、`PIN_RGB_G`、`PIN_RGB_B` | 本組三個已確認 GPIO |
| `RGB_ON_LEVEL` | 已確認的 HIGH 或 LOW；不是大家都填 HIGH |
| `RGB_PROFILE_CONFIRMED` | 接法及電氣條件確認完成後才 true |
| OLED、光敏相關設定 | 保持預設 false／−1，`LIGHT_INTERFERENCE_TEST=false` |

1. 外部模組仍不接，只有裸板 USB。
2. 按 Verify，再按 Upload，等待完成。
3. 關閉 Serial Monitor，拔 USB、PWR 熄滅，再照下一頁接 RGB。

`-1` 是「還沒有指定可用腳位」，不是負一號排針。`true` 是記錄已完成確認，不是略過檢查的開關。

若看到 `U8g2lib.h` 找不到，回程式庫管理員檢查安裝，先不要改接線。

> 每次只送一個小寫字母。

接線核對後接回 USB，開「工具 → 序列埠監控視窗」，選 **115200**。在輸入框打字後按 Enter。

| 送出 | 應看到 | 自己觀察到 |

| o | 全關 | ＿＿ |

## 燈亮，是因為形成了電流回路
> 這張是已確認共陰模式的簡化圖，不是另一張排針順序圖。

{{diagram:rgbcurrent}}

三條支路各有限流電阻，共同端回到 GND。只開紅色時，另兩個通道關閉。本週不做混色或把三個控制腳直接相連。

**計算示例，非本批電流實測：** 假設供應 3.3 V、某一色 LED 壓降 2.0 V、串聯電阻 330 Ω。

```text
電阻兩端電壓 = 3.3 − 2.0 = 1.3 V
電流 = 1.3 ÷ 330 ≈ 0.00394 A = 3.94 mA
```

不同顏色的 LED 壓降可能不同。板上電阻、GPIO 單腳與總電流仍需核對，不能把這個算例當成任一模組的規格。

共陰模式通常 HIGH 亮；共陽模式可能 LOW 才亮。這就是程式要另存 `RGB_ON_LEVEL` 的原因。

## OLED 的四腳，各做不同的事
> 先拔 USB，暫時拆開 RGB 和 ESP32 的連線。

{{photo:OLED_1.jpg|65|已購四針 OLED 正面標示 GND、VDD、SCK、SDA。這是辨識照片，不是通電畫面。}}

| 這片板上的字 | 本課功能 |
|---|---|
| GND | 共同參考與電源回路 |
| VDD | 供電；其他模組可能寫 VCC |
| SCK | 這片已核對 I2C 模組的時脈，程式寫 SCL |
| SDA | 傳送資料 |

別的模組寫 SCK，不一定代表 I2C。七針 SPI 螢幕也不能套用本週四針圖。

安裝支架要留出背面套杜邦線的空間；不要硬推排針或把螺帽鎖到板子彎曲。

## 先上傳掃描程式
> 掃描只問「這個位址有沒有回應」，還不顯示文字。

1. RGB、OLED 都先不接 ESP32。
2. 用「檔案 → 開啟」打開 [I2C 掃描程式](../../../examples/week05_i2c_check/week05_i2c_check.ino)。這是另一支程式，不貼進剛才的程式裡。
3. 在開頭填入本組 `PIN_SDA`、`PIN_SCL`，兩者必須不同。
4. 已完成本批電源、腳序與訊號電位核對後，`ELECTRICAL_PROFILE_CONFIRMED` 才改 true。
5. 裸板接 USB，Verify、Upload；成功後拔 USB，再接下一頁。

| 設定例的來源 | 不能推論的事情 |
|---|---|
| T01 曾使用 SDA8、SCL9 | 所有 ESP32 都應接 8／9 |
| 曾掃到 0x3C | 任一 OLED 都是 0x3C |
| 程式上傳成功 | OLED 已經能顯示 |

`0x` 是十六進位數字的寫法，這裡表示通訊位址，不是腳位編號。

## 兩條供電線，兩條通訊線

USB 拔除。模組已確認適用 3.3 V 供電，SDA／SCL 電位也須相容。

| 起點 | 終點 | 線型 |

## 掃到 0x3C，不等於認出型號
> 開 Serial Monitor，選 115200。

每次開機只掃一次。若錯過紀錄，在接法不變時按 **RST** 重看。

**教學示例，非這次實測：**

```text
event_type=i2c_ack address_7bit=0x3C model=unknown
event_type=scan_finished found=1 model_verified=false
```

| 看見什麼 | 怎麼判斷 |
|---|---|
| 符合模組資料的位址有回應 | 保存完整輸出，下一步才驗證畫面 |
| found=0 | 沒掃到；拔 USB 後查電源、共地及兩條訊號 |
| 多個或不符預期的位址 | 停下核對，不任挑常見數字 |
| blocked | 先查設定；程式沒有開始掃描 |

ACK 是對方的確認回應，像點名時回答「有」。它不告訴你控制器型號，也不證明像素、玻璃或文字畫面正常。

`found=1` 是一個有回應的位址，不必然代表恰好一片正常螢幕。

## 螢幕怎麼收到文字？
> 供電讓它工作，通訊讓它知道要畫什麼。

{{diagram:oledflow}}

ESP32 在這條 I2C 通訊上主動開始傳送；SDA 傳資料，SCL 配合時脈。模組回應自己的位址。

螢幕上的控制器再把收到的內容轉成像素。**128 × 64** 是橫向 128、縱向 64 個像素，不是電壓。

所以接上電源不會自動出現「Hello」。要有正確介面、位址、控制器設定與程式送出的畫面。

同一位址可能用在不同控制器上，SSD1306、SSD1315、SH1106 不能只靠掃描結果混用設定。

## 第二輪只顯示文字
> 回到 RGB／OLED 倒數程式，改選 2。

| 設定名稱 | 本次內容 |
|---|---|
| `LESSON_STAGE` | 2 |
| `PIN_SDA`、`PIN_SCL` | 剛才已確認的 GPIO |

2. 裸板接 USB，Verify、Upload；完成後拔 USB。
3. 依第 {{page:oledwire}} 頁恢復 OLED 接線，核對後上電。RGB 仍不接。

## 先讓 3 變 4，再回到 3
> 這一輪還不能開始倒數。

上電後應看到以下**畫面示意，非實機截圖**：

{{diagram:screen}}

1. 確認四行字都完整、沒有偏移或缺行。
2. 在 Monitor 送 **4**，看 DEMO 變成 4/6。
3. 再送 **3**，看它回到 3/6。
4. 送 **s** 應被拒絕，因為現在只做第 2 輪。

IDLE 是待機；TIME 30 s 是準備的總時長，還沒開始走。NOT RUNNING 是未進行中。NOT SCORE 提醒這個數字**不是實際得分**。

如果畫面不完整，保存照片後拔 USB，核對驅動、解析度與位址。ACK 有回應仍可能畫錯。

## 程式先畫在記憶體，再送到螢幕

{{diagram:buffer}}

`clearBuffer()` 清掉的是 ESP32 記憶體裡準備傳送的影像，不是切斷 OLED 電源。`sendBuffer()` 才把這張圖送出去。

這支程式每次重畫整張，避免把新的短字疊在舊的長字上。傳送要花時間，畫面是某個時間點的結果，可能比目前狀態稍舊。

128 × 64 的單色像素緩衝需要：

```text
128 × 64 ÷ 8 = 1024 bytes
每個像素一個 bit；8 bits = 1 byte
```

這只算像素資料，不是整支程式的全部 RAM。螢幕先使用英文字與數字；中文字另需適用字型與實機排版，不直接換中文字就當完成。

## 送 s，等它自己到期
> 先不按其他命令，觀察一個完整的 30 秒。

| 開始後的經過時間 | 程式預期狀態與燈色 |
|---|---|
| 0～不到 3 秒 | RUNNING；綠 |
| 3～不到 6 秒 | RUNNING；紅 |
| 6～不到 9 秒 | RUNNING；綠 |
| 此後每 3 秒 | 紅綠輪換 |
| 檢查到經過至少 30 秒 | EXPIRED；全關；剩餘 0 |

同時對照 **實物燈、OLED 文字、Serial 的 phase**。GREEN / COVER 是綠燈提示，RED / WAIT 是紅燈提示；這週遮住 KY 也不會因此得分。

到期後再送 s，程式會拒絕。送 **z** 回待機，再送新的 **s**，才開始下一輪。

保存一輪的開始、換色與到期紀錄，以及實物照片。不要把每一次螢幕刷新當成一秒。

## x 是中止，z 是重新準備

1. z 回 IDLE，s 開始新一輪。
2. 進行中再送 s，確認它不重設起點。
3. 送 **x**：應變 ABORTED、RGB 全關，剩餘時間停止變化。
4. 再送 s，應被拒絕。
5. 送 **z**，回到 IDLE、30 秒；還不計時。再送 s 才重新開始。

{{diagram:states}}

中止不是暫停後續跑。z 會準備新一輪，不接著剩下的秒數走。

<aside class="safety">x 是軟體命令，不是切斷電源。發熱、異味、持續重啟或需要換線時，直接拔 USB，不靠送 x 代替斷電。</aside>

## 30 秒不是「畫面減 30 次」
> 先看開始時刻，再看現在時刻。

以下為**教學假資料**：開始時 `millis()` 是 10000，現在是 11500。`millis()` 表示開機以來的毫秒。

{{diagram:time}}

```text
經過時間 = 11500 − 10000 = 1500 ms
剩餘時間 = 30000 − 1500 = 28500 ms = 28.5 s
```

開始時刻、目前時刻是時鐘上的位置；經過時間和剩餘時間是長度。1 秒 = 1000 毫秒。

程式每次用時間差重算，就算畫面少更新幾次，也不會因此補回幾秒。若已過 30 秒，剩餘值為 0，不顯示負數。

<!-- page: rounding | 看看顯示怎麼取整 -->
## 還有 1 毫秒，畫面也可能寫 1 秒
> 畫面整秒方便讀，判定到期仍使用毫秒。

| remaining_ms | 顯示 seconds | 真正意思 |
|---:|---:|---|
| 28500 | 29 | 還有 28.5 秒，不是完整 29 秒 |
| 1499 | 2 | 還有 1.499 秒 |
| 1000 | 1 | 還有 1 秒 |
| 1 | 1 | 只剩 0.001 秒 |
| 0 | 0 | 已到期 |

```text
顯示秒數 = (剩餘毫秒 + 999) 整數除以 1000
```

這是向上取整。例如 (1499 + 999) ÷ 1000，取整數結果為 2。

畫面還可能是上一張舊圖。因此，不能拿螢幕仍顯示 1，主張時鐘已到期後還能繼續。

若直到經過 31200 ms 才再次檢查，仍應到期、剩 0；但已晚了 1200 ms，不能宣稱精準在第 30 秒停止。

## 程式的狀態，和你看到的畫面
> 以下示例分行方便閱讀，不是新的實測結果。


| 欄位 | 判讀 |

## 只把刷新間隔 200 改成 1500
> 保持總時長 30000、換色間隔 3000 不變。

**先預測：** 螢幕較慢刷新，這輪會不會變成 225 秒？會不會跳秒？

1. 先保存原設定 200 ms 那一輪的紀錄。
2. 只改 `DISPLAY_INTERVAL_MS = 1500`，Verify、Upload；接線不變，不移線。
3. 送 s，保存 `remaining_ms`、`uptime_ms` 與到期結果，觀察畫面更新。
4. 比較兩版本，完成後改回 **200**，重新上傳、確認正常。

| 保持不變 | 唯一改變 |
|---|---|
| 同組板、模組、接線、30 秒、3 秒換色 | 畫面更新間隔 200 → 1500 ms |

預期畫面較常跳秒或落後，**不應把 30 秒乘 7.5 變 225 秒**。剩餘量仍由時間差計算。

這是刻意改程式，不是硬體突然壞了。紀錄能比較軟體判定；沒有外部時間參考，不能宣稱已驗證時鐘的絕對精度。

## 程式不必為了等一秒停住

{{diagram:loop}}

本例在倒數迴圈用時間差判斷，不用 `delay(1000)` 讓整個迴圈停一秒。開機時的 delay 是另一件事，不是倒數算法。

畫面約每 200 ms 更新；一般狀態紀錄約每 500 ms 輸出，狀態改變時也會印。這兩個間隔都不是「一秒」的定義。

但 I2C 傳一張圖仍要花時間。程式傳完重新讀時鐘、再次判斷到期，不能保證零延遲。

程式的 20 ms 匯流排逾時設定，也不是整張圖、整個中止流程一定在 20 ms 內完成的保證。

## 按鈕是命令，時間仍用 millis

{{diagram:cumulative}}

```text
任一按鈕按下的電流：
3.3 V → 晶片內部上拉電阻 → 對應 GPIO → 按鈕 → GND
```

GPIO4／5 都只讀按鈕，不供應螢幕電力。SDA／SCL 是另一組不同的 GPIO。

| Monitor 沒連上 | 查 COM 接頭、實際埠號、Board、115200；不先改 OLED 線 |
| r 卻亮綠 | 拔 USB 後沿 R／G 逐條查，不修改紀錄掩蓋 |
| OLED 掃不到 | 拔 USB 後查電源、GND、SDA、SCL，不提高電壓 |
| 有 ACK 但畫面亂 | 保存照片，查控制器、解析度、驅動與位址格式 |
| s 被拒絕 | 必須第 3 輪、IDLE、無顯示故障；不是連按 s |
| f 後螢幕不動 | 先看 Serial 的 ABORTED，這可能就是舊畫面 |
| 發熱、異味、重啟 | 立即拔 USB，停止本次實驗再排查 |

求助時附上：程式設定、完整訊息、接線照片、最後一個命令。不要只說「螢幕不能用」。

## 不用先看懂每一行

| 要找的行為 | 程式位置 |
|---|---|
| 哪些器材可以啟動 | 開頭設定、`profileReady()` |
| 剩餘時間 | `remainingAt()`，從開始時刻算差 |
| 顯示整秒 | `displaySeconds()`，向上取整 |
| 換色與到期 | `advanceTimer()`，先判期限 |
| s、x、z、f、c | `handleCommand()`，依狀態處理 |
| 四行螢幕內容 | `drawSnapshot()` |
| 不斷重複檢查 | `loop()`，傳圖前後都檢查時間 |

Wire 掃描用 7 位址，例如 0x3C。主程式傳給 U8g2 時才乘 2，這是 API 格式要求，**不是掃到了第二個位址**。設定表仍填原來的 0x3C。

Verify 的 `Sketch uses` 比例對照的是設定的應用程式分割區，不是整片 16 MB Flash；`Global variables use` 也不是執行時所有 RAM、堆疊與 PSRAM 用量。

這些編譯數字不能證明接線或畫面正常。後面兩支完整程式保留未確認時的阻擋設定，依課堂設定再使用。
